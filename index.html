Cases

Each is a real production incident. The label names the failure class, because the useful part is rarely the fix — it's what made the bug survive the checks that should have caught it.

Idempotency

A retry turned one customer order into three

Symptom
One real order sat in the dispatch queue three times. Nobody had done anything twice. The business could have sent three deliveries and billed for one.
The chain
A launch routine copied a 53 MB SQLite file inline while the server was already accepting traffic. A concurrent write hit database is locked. The intake webhook returned 500. The upstream SMS gateway did what gateways do and retried — and the retry landed as a brand-new row, because the endpoint had no idempotency key.
Fix
Persist the gateway's own receipt timestamp as an external key and let a unique database constraint arbitrate, rather than an application-level "have I seen this?" check that races under exactly the conditions that caused the bug. Separately, moved the database to WAL so a backup stops blocking writers at all.
Proven by
Removing the constraint and confirming the test went red — a fix that can't be made to fail hasn't been tested. Negative control: a customer genuinely ordering the same thing twice must still produce two records.
Silent data loss

An import reported success and dropped 1,604 rows

Symptom
None. A 265,000-row message archive imported cleanly, no errors, no warnings. The absence of a symptom is why it's here.
What hid it
The parser matched one row shape and quietly skipped another — group messages, which included real customer orders. Found by ignoring the importer's own reporting and counting raw rows in the source file instead: 263,857 matched against 265,462 present.
Also found
27,264 dates silently failed to parse because one month was abbreviated with four letters where the format string expected three. Recovered data was material — a single year's records went from 155,546 to 181,371.
Rule since
A clean exit is not verification. Reconcile against an independent count taken from the source, not from the tool doing the work.
False negative

The fix that would have looked correct and done nothing

Symptom
A Spanish-derived character rendered wrong throughout imported customer data — in names, and in street addresses.
The trap
The obvious fix is Unicode normalization. But the source contained a combining diaeresis where a tilde belonged, and Unicode has no precomposed form for that letter-plus-diaeresis pair — so normalization is a silent no-op. The fix would have passed review, shipped, and changed nothing.
Fix
Swap the combining mark first, then normalize, scoped to the single affected letter so legitimate umlauts elsewhere in the data survive. A test now guards the no-op case specifically, so nobody re-introduces the plausible version.
Scope correction
The reported scope was ten fields. It was twenty — and nine of them were street addresses, which is what a courier actually reads on the way to a delivery. Worth more than the names.
Silent data loss

Seven files vanished while the tool reported success

Symptom
None again. An 81 GB personal archive migrated between machines. Exit code 0. File counts matched on both sides.
What hid it
The destination filesystem was case-insensitive and the source was not. Files differing only in capitalization collapsed into each other on arrival, and the counts still matched because the collisions happened before anything was counted.
Caught by
Checksumming both sides instead of trusting the transfer. Seven videos, roughly 7.7 GB, were already gone — and would have stayed gone, since the next step was to reformat the source.
Rule since
Verify by hash, never by count and never by exit code. Both of those agreed with each other and were both wrong.
Unverified handoff

An AI-generated audit that was fabricated end to end

Symptom
A session summary written by an AI assistant reported that only eight database migrations existed, that one was destructive and unapplied, that a model field was missing, and that the framework was two major versions behind.
Reality
Twenty-two migrations, all applied. The field present. The framework current. Every specific claim was confidently stated and wrong.
Cost
Five tickets deferred for no reason, and a full working session spent proving nothing was broken.
Response
A written standing rule: any handoff's claims about the state of the codebase are untrusted until re-checked against the repository — migrations listed, fields grepped, versions printed. Roughly one minute of checking against a session of phantom work. This is why I run AI-assisted and still verify before I act.
Premature diagnosis

A plausible lead shipped the wrong fix to a live client machine

Symptom
A client reported the register crashing during service, and sent a screen recording with the report.
What went wrong
A plausible explanation presented itself early and fit the description. I shipped against it. It wasn't the fault — decoding the recording frame by frame afterwards showed a different failure entirely, and the original one was still there.
Rule since
When a report ships evidence, decode all of it and reproduce the actual failure before writing a line of the fix. A hypothesis that explains the symptom is not a verified hypothesis — plausibility is the thing that makes a wrong diagnosis expensive.

How I work

I use AI assistants throughout and treat their output as draft work. The practices below are what make that safe rather than fast-and-sorry.

Prove the test can fail
After a fix passes, I remove the fix and confirm the test goes red. A green test that was never shown to fail is decoration.
Run a negative control
Every change gets a case that must not change. Deduplication is only correct if a genuine repeat still gets through.
Run a positive control
When a query returns nothing, I prove the query works before I conclude the data is absent. An empty result and a broken filter look identical.
Verify claims against the code
Line numbers, field names, migration state, versions — checked in the repository before they shape any decision. Notes and summaries are untrusted on matters of fact.
Small, reviewable diffs
Scoped commits with the reasoning written down, so a reviewer can follow the argument rather than reverse-engineer it.
Deploy with a way back
Snapshot first, record the rollback target before starting, verify the live artifacts independently afterwards rather than trusting the deploy script's own report.
